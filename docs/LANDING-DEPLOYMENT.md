# Выкладка лендинга

Лендинг и админка собираются вместе. Публичный адрес после успешной выкладки:
`https://schimmer-glanz.exe.xyz/product/`.
Корень `/` сейчас открывает вход/рабочее пространство админки, а не лендинг.

## Где лежат файлы

| Назначение | В репозитории | На сервере после выкладки |
| --- | --- | --- |
| Страница лендинга | `web/app/product/page.tsx` | `public/product/index.html` внутри `/srv/nfc` |
| Стили и анимация | `web/app/product/product.css` | Собранные файлы в `/srv/nfc/public/_next/` |
| Немецкие и английские тексты | `web/messages/de.json`, `web/messages/en.json` | Включены в сборку |
| Картинки интеграций | `web/public/integrations/` | `/srv/nfc/public/integrations/` |
| Полная готовая сборка | `web/out/` после `pnpm build` или `pnpm verify` | `/srv/nfc/public/` |
| Приём заявок | `server/routes/trial-requests.js` | `/srv/nfc/routes/trial-requests.js` |
| Таблица заявок | `server/db/migrations/024_trial_requests.sql` | Применяется мигратором к Postgres |

Не переносите только `product/index.html`: странице нужны общие JS/CSS из `_next`
и другие файлы полной сборки. Форма отправляет `POST /public/trial-requests` на
тот же сервер. Заявки доступны суперадминистратору через `/platform/`; этот
обработчик сохраняет запись в базе, но сам не отправляет письмо на почту.

## Обычный способ: GitHub Actions

1. Проверить и влить PR в `proximata/nfc-timesheets`, ветку `main`.
2. Открыть GitHub → Actions → **Deploy (API + admin)**.
3. Дождаться успешного выполнения. Изменения `web/`, `server/` или `ops/` в
   `main` запускают этот workflow автоматически. Создание PR и push нашей
   рабочей ветки сами по себе эту выкладку в основном репозитории не запускают.
4. Проверить `/product/`, DE/EN, мобильную ширину и отправку согласованной
   тестовой заявки; убедиться, что заявка появилась в панели платформы.

Конфигурация: `.github/workflows/server-deploy.yml`. Она запускает единый
сценарий `ops/deploy.sh`: проверки, сборка, копирование, миграции, перезапуск
`nfc-api`, проверка соответствия файлов. Для этой объединённой ветки нужен
полный деплой: она содержит также API и миграции рабочих пространств,
заявок и запланированных смен.

В Settings → Secrets and variables → Actions основного репозитория нужны:

- `SERVER_DEPLOY_SSH_KEY`: ключ, зарегистрированный в exe.dev и имеющий доступ
  к серверу и необходимому sudo.
- `WEB_MAPS_KEY`: браузерный ключ Google Maps для админки, с разрешённым
  адресом `https://schimmer-glanz.exe.xyz/*`.
- `WEB_SENTRY_DSN`: необязательный адрес телеметрии веб-интерфейса.

Наличие и исправность этих секретов здесь не проверялись. Рабочая конфигурация
API/базы хранится на сервере в `/etc/nfc/env`; её не нужно копировать в Git.

## Ручной запуск того же сценария

Из корня проверенного checkout на Linux/WSL или macOS с Node.js 22+,
Corepack/pnpm, Bash, rsync и настроенным SSH:

```bash
./ops/deploy.sh
```

Перед запуском должны быть установлены зависимости `server/` через
`pnpm install --prod --frozen-lockfile`; шаги начальных проверок импортируют
серверные модули. Передайте `NEXT_PUBLIC_GOOGLE_MAPS_KEY` и, при необходимости,
`NEXT_PUBLIC_SENTRY_DSN` через окружение либо настроенное хранилище psst.
Сценарий устанавливает зависимости веба, запускает `pnpm verify` и выбирает
сервер из `ops/branding.json` (`apiHost`). Из обычного PowerShell напрямую
этот Bash-сценарий не запускается; проще использовать GitHub Actions.

Это команда реального деплоя: она применяет миграции и перезапускает API.
При отказе проверки миграций устраните указанную причину, не обходите проверку.
Перед production-выкладкой должна быть доступна актуальная резервная копия базы.

`timesheets.exe.xyz` — отдельный постоянный домен NFC-меток. Лендинг туда
не выкладывается; `ops/tag-host/deploy.sh` для этой задачи не нужен.

## Что ещё пока является заглушкой

Book a call показывает состояние недоступного бронирования. Microsoft sign-in,
Microsoft 365, Outlook и Google Workspace обозначены как будущие интеграции.
Успешная выкладка не подключает эти внешние сервисы автоматически.

Эта инструкция проверена по коду репозитория 23.09.2026. В рамках подготовки
PR production-сервер не обновлялся, live-секреты и состояние сервера не проверялись.
