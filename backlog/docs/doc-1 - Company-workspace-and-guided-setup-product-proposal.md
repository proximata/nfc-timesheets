# Кабинет клининговой компании и пошаговый запуск

Статус: предложение для обсуждения, 22 сентября 2026. Код продукта не менялся. Связано с TASK-315 и decision-66. Исследован текущий checkout 56838e4; состояние production-БД не проверялось.

## Для кого

Компания здесь — отдельная клининговая фирма со своими сотрудниками и объектами. Нынешние clients — заказчики уборки внутри такой фирмы. Это разные сущности. Владелец здания получает существующий ограниченный отчёт, а не кабинет с зарплатами.

Предлагаются два интерфейса в одном продукте: наш кабинет управления компаниями и простой кабинет руководителя одной компании. Общие формы, расчёты, API и переводы переиспользуются. Отдельную копию приложения для каждой компании не создаём.

## Что руководитель видит

Пять основных разделов: Обзор, Сотрудники, Объекты, Расчёты, Материалы. Настройки компании и помощь внизу. История уборок доступна с Обзора и из сотрудника/объекта, без ещё одного большого раздела. Контракты и заказчики внутри объекта; склад внутри материалов; расширенный P&L позже. Системные флаги и управление всеми компаниями доступны только нам.

Обзор отвечает на четыре вопроса: кто сейчас отмечен на работе, сколько часов и денег начислено за выбранный месяц, что требует решения, что происходит с материалами. Всегда показывается свежесть данных; открытая смена не доказывает физическое присутствие человека.

Сверху: отмечены на смене; подтверждённые часы; начислено по часам; заявки на материалы. Ниже: незавершённые/спорные смены, ещё не активированные карты, сотрудники без входа и заявки, ожидающие решения. Клик открывает конкретное действие с сохранённым фильтром. Карта остаётся внутри Объектов.

Профиль сотрудника: ставка, история смен с объектами, часы/начисления за месяц, доступ в приложение, проблемы синхронизации. Карточка объекта: адрес и карта, последние уборки, работающие по отметкам сотрудники, часы месяца, зоны/готовность карт, ссылка на отчёт владельцу. Термин «зона» можно объяснять как «точка отметки», сохраняя существующую модель и обязательную проверку карты оператором.

Графики: часы по неделям; начисления по сотрудникам; труд и известные расходы на материалы по месяцам. Один период на всех карточках, таблицах, графиках и экспорте. Незаполненная стоимость не превращается в ноль. «Здесь сегодня никто не убирал» не называется нарушением графика: календаря ожидаемых уборок сейчас нет.

## Лёгкая настройка

В нашем кабинете: создать рабочее пространство, указать email администратора, сформировать ограниченное по времени приглашение. Письмо/ссылка приглашения требует новой серверной логики; это не готовая существующая функция. Получатель сам задаёт пароль. Показываем статусы приглашён / настраивается / работает / приостановлен.

После первого входа — большая кнопка «Лёгкая настройка» и сохраняемый прогресс:

1. Компания: название, язык; логотип и контакты необязательны. Предзаполнить известное из приглашения. Для первого запуска сохранить текущие EUR и Europe/Vienna; мультивалютность не обещать.
2. Объекты: название и адрес с подсказкой/проверкой карты. Можно добавить несколько; контакты заказчика, договор и площадь раскрываются как дополнительные поля.
3. Сотрудники: имя и обязательная положительная часовая ставка; телефон/email для выбранного способа доступа. Добавление списком, код/приглашение из существующего процесса подключения сотрудника.
4. Начать работу: назначить оператора, записать/привязать и проверить хотя бы одну карту, подключить работника к приложению и увидеть первую реальную смену. Это отдельный понятный этап: три заполненные формы ещё не означают готовый учёт.

Каждый шаг делает реальное сохранение через общие API, повторное открытие не создаёт дубли. Можно прерваться и вернуться. Готовность считается по фактам, а не посещению страниц: объект есть, сотрудник есть, карта проверена, сотрудник вошёл. Пробный режим использует изолированные демонстрационные данные, не добавляет выдуманные оплачиваемые смены.

После мастера остаётся небольшой чек-лист следующих действий. Инструкция встроена рядом с действием: короткая фраза «зачем это» и одна следующая кнопка, без обязательного чтения длинного руководства.

## Что переиспользуется из текущего кода

- web/app/workers/page.tsx, WorkerPanel: сотрудники, ставки, доступ, деактивация.
- web/app/locations/page.tsx, BuildingPanel, AddressSearch: объекты, адреса/карта, зоны и отчёт владельцу.
- web/app/shifts/page.tsx и lib/shifts.ts: кто/где/когда, фильтры и исправление спорных смен.
- web/app/payroll/page.tsx и lib/payroll.ts: период, часы x ставка, исключения, CSV.
- web/app/material-requests/page.tsx и lib/materials.ts: заявка -> одобрено -> заказано -> получено; отказ отдельно.
- web/app/analytics/page.tsx и pl/page.tsx: часть месячных агрегатов для графиков, а не весь сложный интерфейс.
- web/app/reinigung/page.tsx: ограниченный отчёт заказчику объекта.
- next-intl, формы, панели, ошибки/пустые состояния и общие DE/EN переводы.

Переиспользовать бизнес-логику можно, но каждый существующий запрос и действие сначала должен получить границу компании. Текущий доступ admin нельзя выдавать другой клининговой фирме как якобы ограниченный.

## Существенные пробелы

1. Изоляция компаний пока не реализована в исследованном коде. Decision-66 описывает tenants/tenant_id и отдельно откладывает RLS, но текущие server/db/migrations, lib/auth.js и lib/db.js даже этого основания не содержат: tenant_id/RLS не найдены, admin-сессия не несёт компанию, выборки admin общие. Документ не равен работающей миграции. TASK-315 остаётся открытым.
2. Нынешний расчёт умножает часы на ТЕКУЩУЮ ставку сотрудника: изменение ставки меняет оценку прошлого месяца. Для достоверных сравнений нужна история ставок с датой действия либо утверждённые неизменяемые расчёты с явными корректировками.
3. Начислено не равно выплачено или долгу. Журнал фактических выплат/авансов/корректировок не найден. Пока показываем «начислено по учёту часов». Для «осталось выплатить» нужны отдельные записи выплат, включая частичные, и понятный расчёт остатка. Банковский перевод из кабинета не входит в первую версию.
4. Материалы: есть заявки и стоимость закупок, но отсутствующая цена не означает бесплатную покупку, а статус «заказано» не подтверждает оплату. Не называть эти суммы банковскими расходами. Существующее распределение материалов по объектам пропорционально часам сохраняется (decision-6).
5. Нужны создание рабочего пространства/приглашение администратора, серверное состояние настройки, роли и проверки доступа. Нельзя решить это только спрятанными пунктами меню.

## Предлагаемая техническая основа

Одна PostgreSQL, отдельный tenant_id для данных каждой клининговой фирмы и RLS как дополнительный барьер на уровне базы, в направлении decision-66. Компания определяется из проверенной сессии. Все бизнес-сущности должны быть изолированы: не только работники/объекты/смены, но и операторы, заказчики, контакты, материалы, склад, договоры, доходы, приглашения и ссылки отчётов. Межфирменные связи запрещаются составными ограничениями, а не только UI.

Текущий pool.query не задаёт контекст компании. При реализации нужен общий серверный механизм контекста внутри транзакции на одном соединении и корректная роль БД без обхода RLS. Политики, права, ссылки и экспорт проверяются двумя тестовыми компаниями; фильтр в браузере не является изоляцией. PostgreSQL owners/superusers могут обходить RLS: https://www.postgresql.org/docs/16/ddl-rowsecurity.html .

Общие приложение и постоянный tagHost можно сохранить как целевую модель. Глобально уникальный UUID сам по себе не даёт права на чужую зону: после чтения карты сервер обязан сверить компанию работника/оператора и зоны. До входа публичный ответ не раскрывает данные чужой компании. Правило для человека, работающего одновременно в двух фирмах, требует отдельного решения; начальный вариант — одна активная компания на сессию с явным переключением, без смешивания офлайн-очередей.

Наш служебный доступ к данным компании должен быть отдельным, явным и журналируемым действием. Простое добавление роли superadmin не должно автоматически делать обычные маршруты неограниченными. Внешний вид/мобильность кабинета согласовать с актуальными ADR; в текущем CSS уже есть адаптивная админка, хотя старые инструкции ещё упоминают desktop blocker.

## Последовательность

1. Согласовать этот состав и показать кликабельный прототип обзора/мастера на вымышленных данных.
2. Реализовать и доказать разделение двух компаний: чтение, запись, поиск, отчёты, экспорт, прямые ID, NFC и фоновые задания; сохранить данные существующей фирмы.
3. Создание доступа и мастер; адаптированные существующие экраны сотрудников/объектов/смен/расчётов/материалов; DE и EN одновременно. Успешный запуск заканчивается первой подтверждённой сменой.
4. Достоверные исторические расчёты, журнал выплат и простые графики. Расширенная прибыльность, расписание уборок, отдельные магазинные приложения и подписочная оплата сервиса — самостоятельные дальнейшие функции.

Для финансовых графиков пилота исправление истории ставок — зависимость, а не необязательная косметика. До этого показывать только корректно подписанный расчёт по текущим ставкам.

Новая реализация не добавлялась в Android PR #6. Это предложение не подтверждает безопасность production-развёртывания для второй компании и не является оценкой сроков.
